⚖️ 2. Design Invariants

The Vault architecture is governed by six invariants that every implementation must satisfy, whether self-hosted on a €4/month VPS or managed by WINDI at enterprise scale.

V1 — SINGLE-TENANT SOVEREIGNTY
One Vault = One Creator
Each Vault serves exactly one creator (or one organization). No multi-tenant mixing of content, keys, or governance data. In VaaS, isolation is enforced via Linux namespaces and dedicated systemd units.
V2 — LOCAL-FIRST PROCESSING
80/20 Compute Rule
All transcoding, packaging, sealing, and manifest generation happens on the Vault's own CPU. No content is ever sent to external services. 80% compute local; only streaming delivery exits.
V3 — IMMUTABLE AUDIT TRAIL
Append-Only Ledger
Every operation (upload, transcode, seal, publish, access) is logged in the Vault's local Ledger (SQLite + SHA-256 chain). Append-only. Deletion requires a logged governance action.
V4 — KEY CUSTODY
Creator Holds Keys
Ed25519 private key resides exclusively on the Vault (or creator's hardware wallet). WINDI never holds, copies, or accesses private keys, even in VaaS. Key rotation supported.
V5 — EXPORTABILITY
No Lock-In
Creator can export entire Vault (content, metadata, Ledger, keys) as portable archive at any time. Migration VaaS↔self-hosted completes within 24 hours for <100GB.
V6 — MINIMUM VIABLE COST
€4-8/month Ceiling
Functional Vault must operate on 2 vCPU, 4GB RAM, 80GB SSD, 2TB bandwidth (≤€8/month). Sovereignty must not be a luxury.

📁 3. Filesystem Layout

Every Vault follows a canonical directory structure. This consistency enables automated provisioning, backup, migration, and debugging.

/srv/windi-vault/ ├── config/ │ ├── vault.yaml # Master config (ports, domain, tier) │ ├── keys/ │ │ ├── creator.pub # Ed25519 public key │ │ └── creator.key # Ed25519 private (chmod 600) │ ├── nginx.conf # Vault-specific nginx server block │ └── ssl/ # Let's Encrypt certificates ├── content/ │ ├── originals/ # Raw uploaded files (never modified) │ ├── onboard/ # 30s MP4 segments (H.264 Baseline) │ ├── hls/ # Adaptive streaming segments │ │ └── {content_id}/ │ │ ├── master.m3u8 │ │ ├── 1080p/ 720p/ 480p/ 360p/ │ ├── jmpg/ # Assembled .jmpg binaries │ └── thumbnails/ # Auto-generated preview images ├── data/ │ ├── ledger.db # SQLite Forensic Ledger │ ├── analytics.db # View counts, geo, device stats │ ├── subscribers.db # DID-based access control list │ └── sge_cache.db # SGE risk classifications ├── services/ │ ├── trigger/ # JMPG Trigger (FastAPI) │ ├── streamer/ # HLS auth + delivery (nginx + lua) │ ├── sealer/ # SHA-256 seal + Ledger writer │ ├── gatekeeper/ # DID challenge + tier resolution │ └── analytics/ # Event collector + aggregator ├── logs/ # Structured JSON logs └── backups/ # Encrypted daily snapshots

📌 Write-Once Originals

The originals/ directory is write-once. Once uploaded, files are never modified or moved. All derived content is regenerated from original if needed.

⚙️ 4. Service Topology

The Vault runs five microservices, each as a dedicated systemd unit, communicating via localhost HTTP. Only nginx is exposed to the public internet.

ServicePortStackResponsibility
Trigger9100FastAPIVideo ingest, ffmpeg orchestration, .jmpg assembly
Sealer9101FastAPISHA-256 computation, Ed25519 signing, Ledger writes
Gatekeeper9102FastAPIDID challenge/response, tier resolution, ACL enforcement
Analytics9103FastAPIEvent ingestion, aggregation, dashboard API
nginx443nginx+luaTLS termination, HLS delivery, static .jmpg, reverse proxy

Port range 9100–9103 reserved for Vault services. In VaaS multi-tenant: 9100+N*10 per tenant.

4.1 Request Flow: Stream Access

1Player sends GET to vault_endpoint/v/{id}/master.m3u8 with DID token
2nginx extracts DID token, forwards to Gatekeeper at 127.0.0.1:9102/verify
3Gatekeeper validates Ed25519 signature, checks subscriber DB, returns ALLOW/DENY
4If ALLOW: nginx serves HLS segments. If tier limits: filter manifest profiles
5Analytics receives access event via async POST from nginx lua module

⚡ Performance

Entire flow from request to first HLS segment: <100ms on €4/month VPS. Gatekeeper decision cached 5 minutes per DID.

🚀 6. Provisioning Automation

Vault provisioning is fully automated for VaaS scalability. When a creator subscribes to SEED (€15/month), the following pipeline executes without human intervention.

6.1 Automated Pipeline

1

IDENTITY BOOTSTRAP

Generate UUIDv7 vault_id, create Ed25519 key pair, register DID in WINDI DID Cycle. Private key encrypted at rest (XChaCha20-Poly1305 + Argon2id).

2

FILESYSTEM SCAFFOLD

Create canonical directory structure. Set permissions 750. Initialize SQLite databases with empty schemas.

3

SERVICE DEPLOYMENT

Generate 4 systemd unit files from templates. Set resource limits (SEED: CPUQuota=50%, MemoryMax=512M). Start and enable services.

4

NGINX CONFIGURATION

Generate server block for subdomain. SSL via Let's Encrypt + certbot. HLS delivery, Gatekeeper proxy, static .jmpg hosting. Validate and reload.

5

DNS REGISTRATION

Create A record for subdomain (or CNAME instructions for custom domain). Validate DNS propagation before SSL cert request.

6

SMOKE TEST

Upload 5s test video, run full Trigger pipeline, verify .jmpg SEAL, test HLS streaming, confirm Gatekeeper. If pass: status = ACTIVE.

⚡ Provisioning Time

From subscription to ACTIVE status: <5 minutes. No human intervention. Same pipeline scales to 100+ Vaults.

🔐 7. Security Architecture

7.1 Key Management

  • Ed25519 key pair is root of trust for entire Vault
  • Private key signs manifests, authorizes publication, authenticates admin API
  • Generated on Vault (never transmitted), encrypted at rest: XChaCha20-Poly1305 + Argon2id
  • In VaaS: encrypted key accessible only to vault's Linux user (chmod 600)
  • WINDI operators cannot decrypt without creator's passphrase

7.2 TLS and Transport

  • All external communication: TLS 1.3 only
  • Let's Encrypt auto-provisioned, auto-renewed via certbot timer
  • Internal localhost communication: no TLS (OS loopback isolation)
  • HSTS headers: 1-year max-age, includeSubDomains

7.3 DID Challenge Protocol

1Gatekeeper issues challenge: nonce + content_id + 60s expiry
2Viewer client signs challenge with DID private key
3Gatekeeper verifies signature against DID public key (WINDI registry)
4Check subscriber DB for access rights
5Issue short-lived access token (5-min TTL) → nginx header

7.4 Content Encryption (Optional)

For PREMIUM/PRIVATE tier: HLS segments encrypted with AES-256-CTR. Key unique per content, stored in Sealer DB, deliverable only to authenticated viewers. Onboard segment is never encrypted (must play offline).

📈 8. Scaling Strategy

8.1 Vertical: Single Server Capacity

Single Strato VPS (4 vCPU, 8GB RAM, 200GB SSD, €8/month) serves 20 SEED Vaults. Bottleneck: concurrent transcoding (1-2 vCPU per ffmpeg). Redis-backed job queue serializes transcoding while other operations proceed.

8.2 Horizontal: Multi-Server Federation

  • At 80% capacity (16+ SEED Vaults or avg CPU >70%): new subs → new server
  • Each server fully independent: own nginx, services, DNS
  • No shared state between servers
  • Control Plane tracks inventory + routing, never touches content/keys
  • If Control Plane down: existing Vaults continue serving

8.3 CDN Integration (FOREST/MOUNTAIN)

European CDN layer for high-traffic Vaults. CDN caches only encrypted/public segments. Vault remains origin. Immediate cache invalidation via purge API. Optional per vault.yaml.

💾 9. Backup and Disaster Recovery

Data loss is sovereignty loss. Backup strategy survives hardware failure, accidental deletion, and ransomware.

Daily Incremental Backup

  • rsync-based incremental: content/, data/, config/
  • Encrypted with creator's public key (only creator can decrypt)
  • Retention: 30 days (SEED/GROW), 90 days (FOREST), 365 days (MOUNTAIN)

Ledger Integrity Check

  • Every backup verifies SHA-256 chain of ledger.db
  • If chain broken: alert creator + WINDI monitoring
  • Most recent valid Ledger snapshot preserved separately

Recovery Time Objective (RTO)

TierSizeRTO
SEED/GROW<100GB2 hours
FOREST<500GB8 hours
MOUNTAINAny<1 hour (hot standby)

Export and Migration

windi-vault export generates portable .wva archive (content, DBs, config, encrypted keys). Import on any Linux server with WINDI runtime. Includes SHA-256 manifest for integrity verification. Zero lock-in.

11.2 Debug Procedure (ss+ps FIRST)

⚠️ Standard WINDI Debug Protocol

When service fails: ss -tlnp + ps aux → identify port conflicts + zombies → kill nohup orphans → purge __pycache__ → then restart systemd unit. Prevents zombie holding port.

11.3 Upgrade Path

  • Atomic releases: stop services → replace binaries → run migrations → restart → smoke test
  • If smoke test fails: auto-rollback <30s
  • Content and configuration never modified during updates

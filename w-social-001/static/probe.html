§02 · Data Flow · Conceptual

How the Pipeline Works

The W-SOCIAL-001 pipeline transforms real work output into verified social presence. Each step preserves provenance and ensures human oversight.

01
CAPTURE
User completes work in WINDI module. System detects "atom of authority" — a publishable insight derived from real intellectual output.
→
02
COMPILE
AI adapts the content for target channel (LinkedIn, Telegram, etc.) while preserving origin reference and applying tone constraints.
→
03
APPROVE
Human explicitly approves the publication. This is the I9-P Protocol in action — AI proposes, human decides. No bypass possible.
→
04
SEAL
Publication is cryptographically sealed with SHA-256, anchored to Forensic Ledger, and a public verify_url is generated for proof.
What travels in the pipeline
  • Actor DID (cryptographic identity)
  • Source reference (origin document)
  • Content hash (SHA-256 integrity)
  • Human approval flags
  • Target channel specification
  • Timestamp (ISO 8601)
What becomes public
  • Seal ID (verification handle)
  • Verification status (VERIFIED/REVOKED)
  • Publication timestamp
  • Channel used
  • Source type (category, not content)
  • Content hash (proof, not content)
Never exposed publicly
  • Original document content
  • Excerpt text
  • Actor personal name
  • Internal system identifiers
  • Client information
  • Internal port mappings

§03 · Invariants Probe · Como testamos no PoC

As três perguntas que o primeiro utilizador vai responder

Cada invariante constitucional traduz-se num teste de comportamento observável. Não basta o sistema respeitar a lei — o utilizador precisa de sentir que a lei existe e que o protege.

I-SOC-001 · PROVENANCE INVARIANT

O utilizador sente que o conteúdo é genuinamente seu?

Observar se o utilizador edita o texto compilado ou se publica directamente. Edição mínima = alta fidelidade à origem. Reescrita completa = falha de I-SOC-001 na prática — a IA não captou a essência real do documento.

✓ PASS: publica com ≤ 2 edições ✗ FAIL: reescreve completamente ✗ FAIL: diz "isto não é meu"
I-SOC-002 · HUMAN SEAL INVARIANT

O utilizador sente controlo real no momento da aprovação?

O checklist de aprovação (três pontos) deve criar fricção intencional positiva — não burocracia. O utilizador deve sentir que está a assinar, não a carregar num botão de confirmação genérico. Observar tempo gasto na etapa de aprovação e linguagem corporal/verbal.

✓ PASS: lê cada item antes de marcar ✓ PASS: pausa no último item (ledger consent) ✗ FAIL: clica tudo sem ler ✗ FAIL: sente que é burocracia
I-SOC-003 · VERIFICATION INVARIANT

O verify_url aumenta ou reduz a confiança do utilizador para publicar?

Este é o teste mais importante do PoC. O seal_id e o verify_url na confirmação final devem criar sensação de permanência e responsabilidade — não ansiedade. Se o utilizador reagir com "ah, fica gravado para sempre?" de forma negativa, a framing precisa de ajuste. Se reagir com "isto é poderoso", o valor está validado.

✓ PASS: "isto dá-me confiança" ✓ PASS: pergunta como partilhar o link ✗ FAIL: "não quero que fique registado" ✗ FAIL: ignora completamente o seal
HIPÓTESE CENTRAL · VALIDAÇÃO FINAL

O utilizador sente que o social emergiu do fluxo de trabalho — não que saiu de uma ferramenta separada?

A pergunta definitiva. Perguntar directamente: "Sentiste que publicaste a partir do teu trabalho, ou que foste usar uma ferramenta de redes sociais?" A resposta a esta pergunta valida ou invalida a hipótese central do produto.

✓ "publiquei o meu trabalho" ✗ "usei uma ferramenta de social"

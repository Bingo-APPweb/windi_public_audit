## 1. DIAGNÓSTICO: Caos Arquitectural

### 1.1 Múltiplas Fontes de Verdade (Problema Crítico)

| Base de Dados | Localização | Tabela Principal | Schema |
|---------------|-------------|------------------|--------|
| DID Genesis | `/opt/windi/did-genesis/did_genesis.db` | `identities` | DID + passphrase_hash + tier |
| Wallet | `/opt/windi/data/wallet.db` | `wallet_human` | human_id + fingerprint + pubkey |
| WINDI-LAW | `/opt/windi/windi-law/identity-gate/windi_law_identity.db` | `admins` | email + DID + fingerprint |
| WINDI-Travel | `/opt/windi/windi-travel/identity-gate/windi_travel_identity.db` | `admins` | email + DID + fingerprint |

**Problema:** 4 bases de dados independentes que não sincronizam. Um DID pode existir numa e não noutra.

---

### 1.2 Múltiplos Mecanismos de Validação

| Serviço | Porto | Mecanismo | Endpoint |
|---------|-------|-----------|----------|
| DID Genesis | :8096 | Cookie `windi_did_session` | `/api/genesis/validate` (requer cookie) |
| WINDI-LAW | :8122 | Token de sessão | `/identity/{did}` |
| WINDI-Travel | :8126 | Token soberano | `/auth/validate` |
| VERA | :8150 | Cross-validation | Tenta 3 serviços em cascata |
| W-LAB | :8151 | Validação local | `validate_did()` interno |
| Constitutional | n/a | Cross-validation | `cross_validate_did()` |

**Problema:** Cada serviço implementou validação própria. Não há protocolo unificado.

## 2. FLUXO DE FALHA (O Que Aconteceu)

```
1. User (Human Dragon) tenta aceder W-Enterprise-001
2. Frontend envia DID: did:windi:dragon-001
3. VERA tenta validar em :8096/session/validate/{did}
   → 404 (endpoint não existe!)
4. VERA tenta validar em :8122/identity/{did}
   → Pode falhar se WINDI-LAW não conhece o DID
5. VERA usa fallback "graceful pass"
   → tier=SEED (ERRADO! Deveria ser ORACLE)
6. User tem acesso limitado ou bloqueado
```

**Causa raiz:** VERA chama endpoint que não existe no DID Genesis.

## 9. IMPLEMENTAÇÃO §173 — DID Simplification

### 9.1 Módulo Python Unificado

**Ficheiro:** `/opt/windi/shared/did_validator.py`

```python
from shared.did_validator import validate_did, DIDResult

result = await validate_did("did:windi:dragon-001")
if result.valid:
    print(f"Tier: {result.tier}")  # ORACLE
    print(f"Access: {result.access}")  # ["*"]
```

**Features:**
- `validate_did()` — async validation against Genesis
- `validate_did_sync()` — sync version for non-async contexts
- `DIDResult` — dataclass with all DID info
- `DIDTier` — tier constants and helpers

### 9.2 JavaScript Frontend Standard

**Ficheiro:** `/opt/windi/shared/static/windi-did.js`

```html
<script src="/shared/windi-did.js"></script>
<script>
    // Get current DID
    const did = WindiDID.get();

    // Validate against Genesis
    const result = await WindiDID.validate(did);
    if (result.valid) {
        console.log(`Tier: ${result.tier}`);  // ORACLE
    }

    // Migration from legacy keys
    WindiDID.migrateFromLegacy();
</script>
```

**Features:**
- `WindiDID.get()` / `set()` / `clear()` — localStorage management
- `WindiDID.validate()` — validate against Genesis
- `WindiDID.migrateFromLegacy()` — auto-migrate from old keys
- `WindiDID.isAtLeast(tier, minimum)` — tier comparison

### 9.3 Genesis Lookup Endpoint

**Endpoint:** `GET /api/genesis/lookup/{did}`

```bash
curl -s "http://localhost:8096/api/genesis/lookup/did:windi:dragon-001"
```

**Response:**
```json
{
    "valid": true,
    "did": "did:windi:dragon-001",
    "tier": "ORACLE",
    "tier_level": 4,
    "access": ["*"],
    "display_name": "Human Dragon",
    "source": "W-DID-GENESIS"
}
```
